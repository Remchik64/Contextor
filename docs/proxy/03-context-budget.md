# 03 — Бюджет контекста

`SPEC` — если не помечено иначе. Документ о том, как измерить буфер и когда сжимать.

---

## 1. Суть проекта в одном механизме

Буфер контекста — настраиваемый ресурс: 4000, 8000, 16000, 32000 токенов. Пока он не
переполнился, надо извлечь самое ценное и разложить по местам. Потом буфер обнуляется,
модель получает чистые данные и продолжает.

Этот документ описывает **триггер** этого процесса. Без работающего триггера всё
остальное — набор модулей, которые ничем не управляют.

---

## 2. Что делает текущий код (проверено)

`BROKEN` Решение о сбросе принимается по **количеству сообщений**, а не по токенам:

```python
# src/contextor/core/orchestrator.py:285-315
def _should_soft_reset(self, cci_score: float) -> tuple[bool, str]:
    turns = self._turns_since_reset
    if turns >= self._max_turns_without_reset:              # 16, захардкожено
        return True, "hard_limit"
    if len(self._chat_history) > self._context_window_size: # 12 СООБЩЕНИЙ, захардкожено
        return True, "history_overflow"
    if cci_score < self._cci_reset_threshold and turns >= self._min_turns_between_resets:
        return True, "low_coherence"                        # 0.55, захардкожено
    return False, "ok"
```

Константы заданы в `orchestrator.py:87,92-94`. Секция `memory.adaptive_reset` из
`config.yaml` **не парсится вообще** — в `MemoryConfig` (`engines/config_loader.py:65-81`)
таких полей нет. `context_window_messages: 12` парсится (`config_loader.py:209`), но в
логике не используется — захардкожено то же число, поэтому подмена незаметна.

### Следствие: `num_ctx` ничем не управляет

`EXISTS` `num_ctx` (селектор 4K/8K/16K/32K в UI) применяется только как опция окна
модели: `dual_model.py:199` для генератора, `utility_worker.py:74-85` для utility. В
решении о сбросе он не участвует. На прокси-пути OpenAI он и вовсе захардкожен обратно
в `4096` (`api/system.py:388`).

**Что это значит практически:**

| Ситуация | Что происходит |
|---|---|
| 12 коротких реплик («да», «ок», «почему?») | Сброс срабатывает, израсходовав ~4% буфера на 16000. Буфер простаивает |
| 12 сообщений с кодом | Буфер переполняется **до** срабатывания триггера. Модель деградирует ровно там, где проект обязан это предотвращать |

Пользователь ставит 16000, ожидая, что система следит за 16000. Фактически система
следит за 12 сообщениями, а 16000 видит только сама модель.

## 3. Правильный учёт токенов

`SPEC` Буфер измеряется в токенах **токенизатором той модели, которая будет работать**.

### Почему не `tiktoken`

`EXISTS` Сейчас бюджет считает `cl100k_base` — токенизатор GPT-4:

```python
# src/contextor/utils/tokenizer.py:6
_encoder = tiktoken.get_encoding("cl100k_base")
```

`BROKEN` Для Qwen/Llama это другая разбивка. На английском расхождение умеренное, на
русском и на коде — существенное, потому что cl100k_base агрессивно режет кириллицу и
редкие идентификаторы иначе, чем BPE этих моделей. Для механизма, вся суть которого в
бюджете, ошибка в десятки процентов означает: вы считаете, что буфер на 80%, а он уже
переполнен.

### Как считать правильно

`SPEC` Через сам движок — он знает свой токенизатор точно.

**llama.cpp** (`llama-server`): эндпоинт `POST /tokenize`, тело `{"content": "..."}`,
ответ `{"tokens": [...]}`. Число токенов — длина массива.

Требует проверки на вашей сборке: `VERIFY` набор эндпоинтов и форма ответа зависят от
версии `llama-server`. Проверить первым делом при внедрении.

**Ollama**: у неё нет прямого `/tokenize` в публичном API. Варианты:
- использовать `/api/embed` и не полагаться на токены — непригодно;
- держать локальный HF-токенизатор, совпадающий с моделью (надёжно, но добавляет
  зависимость);
- для Ollama-режима грубо оценивать и держать запас 15–20%.

`SPEC` Приоритет: llama.cpp через `/tokenize`. Это ваш основной сценарий, и он даёт
точность бесплатно.

### Что именно считать

`SPEC` Считать надо **весь промпт**, а не только историю:

```
fill = tokens(system_prefix)      # включая Context Package и anchor-факты
     + tokens(all messages)       # user + assistant + tool
     + tokens(tools_schema)       # если клиент передаёт определения инструментов
     + reserve                    # место под ответ: max_tokens запроса
```

Последний пункт критичен и обычно забывается: если считать только вход, окно
переполнится ровно на длине ответа. Резерв равен `max_tokens` из запроса.

`SPEC` Кэшировать результат: считать токены заново на каждом ходу дорого (один
HTTP-вызов на движок). Достаточно считать инкрементально — токены неизменного префикса
плюс токены новых сообщений.

## 4. Пороги

`SPEC` Задаются в **долях буфера**, а не в числах сообщений и не в абсолютных токенах:

| Порог | Значение | Действие |
|---|---:|---|
| `warn` | 0.60 | Разрешить `ENRICH`, начать готовить сжатие |
| `soft` | 0.75 | Сжать самый старый блок (мягкое сжатие) |
| `hard` | 0.85 | Сжать всё до последних K ходов (жёсткое сжатие) |
| `abort` | 0.95 | Аварийно: только anchor + последние 2 хода |

`SPEC` Значения выбраны высоко намеренно. Причина — в `01-architecture.md`, раздел 5:
сжатие ломает KV-кэш движка и стоит полного prefill. Частые дешёвые сжатия обходятся
дороже редких дорогих.

`SPEC` `num_ctx` берётся из настроек (4K/8K/16K/32K) и **обязан** быть тем же числом,
которое уходит в движок как размер окна. Сейчас эти два числа живут независимо.

## 5. Политика сжатия

`SPEC` Что остаётся в окне после сжатия:

```
[system]                     # неизменный префикс: роль + Context Package + ANCHOR
[user/assistant × K]         # последние K ходов, K = 4..8
```

Всё, что между ними, заменяется Context Package. `K` выбирается так, чтобы последние
ходы сохраняли локальную связность диалога (обычно 4–6 ходов).

`SPEC` Что делается с выброшенным отрезком, по шагам:

1. **Извлечь адреса** — скрипт проходит по выброшенным сообщениям и обновляет ledger
   (`02-memory-model.md`). Это делается **всегда**, независимо от модели.
2. **Выделить anchor-факты** — решения, контракты, цель, нерешённые ошибки. Они
   становятся постоянной частью префикса.
3. **Сжать остаток в прозу** — координатор. Вход: выброшенный текст. Выход: 200–400
   токенов на английском.
4. **Собрать Context Package** — четыре слоя, слой 3 (код) берётся из ledger, а не от
   модели.
5. **Выгрузить координатора** — немедленно, до отправки запроса в движок.

`SPEC` Шаг 3 — единственное место, где нужна модель. Если он падает, сжатие всё равно
происходит: без прозаической координаты, но с адресами и anchor-фактами. Память
деградирует мягко, а не отключается целиком.

`BROKEN` Сейчас всё наоборот: при отказе модели `DualModelRouter.generate` возвращает
`("", 0, 0)` (`dual_model.py:288-290`), а вызывающий код рапортует успех и добавляет
пустое assistant-сообщение (`orchestrator.py:469`). Отказ выглядит как успешный ответ.

## 6. Связность вместо CCI

`SPEC` Метрика связности нужна для одного: решить, что разговор «поплыл» и адресная
память перестала соответствовать запросам. Но вычислять её эмбеддингами не обязательно.

Дешёвый вариант без модели и без VRAM: **пересечение множеств идентификаторов**.

```
tokens_now  = identifiers(query)              # имена файлов, символов, команд
tokens_prev = union(identifiers(last N turns))
overlap     = |tokens_now ∩ tokens_prev| / |tokens_now|
```

Признак потери нити — падение `overlap` при росте заполнения буфера. Это считается
микросекунды и не требует ни GPU, ни сети.

`BROKEN` Текущий CCI — это BM25 по ключевым словам (`cci.py:71-102`) с шагом, который
**делает метрику неспособной сообщить о проблеме**:

```python
# src/contextor/core/memory/cci.py:206-210
if final_score < self.threshold and self._history:
    prev_score = self._history[-1].coherence_score
    if prev_score >= self.threshold:
        final_score = self.threshold + 0.01
```

Первый ход всегда даёт `1.0` (`cci.py:160-169`) и сохраняется, поэтому все последующие
принудительно поднимаются до `threshold + 0.01`. Проверено запуском: пять намеренно
несвязанных тем подряд (борщ → КХД → ветеринар → kubernetes → ботинки) — все
`coherent=True`, счёт зажат в `0.16`.

Следствие серьёзнее, чем неточная метрика: `needs_context_restore()` всегда `False`, а
это единственное условие вызова извлечения фактов (`orchestrator.py:351`). **WARM-память
пишется и никогда не читается.**

## 7. Проверка

`SPEC` Метрика — удержание адресов через сжатия:

1. Ввести N уникальных адресов (файл + символ + диапазон строк).
2. Прогнать M сжатий буфера (искусственно занизив `num_ctx`, например 2048).
3. Задать по каждому адресу вопрос, требующий точных имён и строк.
4. Посчитать долю корректных.

Ожидаемый результат: baseline падает почти до нуля после первого сжатия, с памятью
остаётся высокой. Измеримо скриптом, воспроизводимо, без фабрикации базовой линии.

`BROKEN` Существующие бенчмарки это не измеряют: `benchmarks/runner.py:113-134` задаёт
базовую линию захардкоженными нулями (`context_tokens=0`, `keyword_recall=0.0`), а
замеряет время двух сравнений в Python. Ни одно из «85% fewer tokens / 100% recall /
5ms per fact» этим кодом не проверяется.
