# 01 — Архитектура прокси

`SPEC` — если не помечено иначе.

---

## 1. Топология

```
┌──────────────┐   OpenAI API    ┌──────────────────┐   OpenAI API    ┌──────────────┐
│   Клиент     │ ──────────────► │  Contextor Proxy │ ──────────────► │ llama-server │
│ (агент, IDE, │ ◄────────────── │  (FastAPI)       │ ◄────────────── │ / Ollama     │
│  curl, SDK)  │   SSE stream    │                  │   SSE stream    │              │
└──────────────┘                 └────────┬─────────┘                 └──────────────┘
                                          │
                          ┌───────────────┴────────────────┐
                          │  Память (RAM, без VRAM)        │
                          │  · индекс адресов              │
                          │  · ledger решений              │
                          │  · архив беседы на диске       │
                          └───────────────┬────────────────┘
                                          │ только на время сжатия
                                  ┌───────┴────────┐
                                  │ Координатор    │
                                  │ (эфемерный,    │
                                  │  swap in/out)  │
                                  └────────────────┘
```

Ключевое: **стрелки вниз не пересекаются со стрелками вправо.** Память и координатор не
участвуют в генерации ответа. Если координатор придётся поднимать на каждом ходу —
архитектура сломана (см. `04-vram-economy.md`).

### Что здесь уже есть

- `EXISTS` FastAPI-приложение: `src/contextor/server.py:20-42`, монтирует `router` на
  `/api/v1` и `openai_router` без префикса (`openai_router` сам несёт `prefix="/v1"`,
  `src/contextor/api/system.py:344`).
- `EXISTS` Эндпоинт `POST /v1/chat/completions`: `api/system.py:371`.
- `EXISTS` Схемы `OpenAIMessage` / `OpenAIChatRequest`: `api/system.py:309-319`.
- `EXISTS` SSE-заглушка `_sse_stream`: `api/system.py:322-341`. В докстроке честно
  написано `Fake SSE streaming` — она режет **уже готовый** ответ на слова.
- `EXISTS` Прокси-путь для «чужих» моделей: `api/system.py:381-397`.
- `BROKEN` В этом прокси-пути **захардкожено `"stream": False`** (`api/system.py:388`),
  то есть потоковый ответ клиенту не поедет, и `num_ctx` захардкожен в `4096`.

Итого: **транспорт есть, решения нет.** Прокси просто перекладывает запрос в Ollama.
Ни памяти, ни бюджета, ни режимов.

## 2. Два сценария — выбрать до начала кодирования

Это развилка, определяющая всю реализацию. Ответ нужен до первой строки кода.

### Сценарий A — прокси прямо перед `llama-server`

Клиент — сам движок или тонкий клиент, который не ведёт свою логику истории
(`curl`, SDK, простой чат-фронт).

- Буфер **целиком ваш**. Клиент присылает то, что вы ему вернули в прошлый раз.
- Сжатие полностью под контролем: вы формируете `messages[]` с нуля.
- Можно жёстко держать окно в пределах `num_ctx` и гарантировать отсутствие переполнения.
- Проще в разы.

`SPEC` Это целевой режим для первой версии.

### Сценарий B — прокси перед агентом (Agent Zero, opencode, Cline)

Агент **сам** ведёт историю и шлёт её целиком, включая свои tool-call'ы, вывод файлов,
результаты команд. Он не знает о вас и не спрашивает разрешения.

- Вы не владеете буфером — вы **вмешиваетесь** в чужой промпт.
- Агент может держать у себя состояние, несовместимое с вашим сжатием (например,
  ожидать, что конкретный tool-result остался в контексте).
- Сжатие середины ломает KV-кэш агентского провайдера, если он тоже кэширует.
- Существенно сложнее и рискованнее.

`SPEC` Реализуется **после** A, как отдельный профиль конфигурации, а не как замена.

Практическое следствие для A: раз буфер ваш, вы можете позволить себе **не хранить
историю в окне вообще**. Окно = `[system с Context Package] + [последние K ходов]`.
Всё, что старше, живёт в памяти и подтягивается адресно. Это и есть «чистые данные»
после обнуления.

## 3. Четыре режима решения

`SPEC` На каждом входящем запросе прокси выбирает одно из четырёх действий. Термины
взяты из архивного `docs/archive/CTX_MODULE_ARCHITECTURE-2026-05-10.md`, где они описаны словами, но не реализованы.

| Режим | Когда | Что делает с `messages[]` |
|---|---|---|
| **PASSTHROUGH** | Буфер в норме, память нерелевантна | Ничего. Байт-в-байт на движок |
| **ENRICH** | Буфер в норме, но запрос задевает известные адреса | Дополняет system-префикс релевантными фактами |
| **COMPRESS** | Заполнение ≥ порога | Заменяет срединный отрезок истории на Context Package |
| **PREFETCH** | Новый чат, но есть память по теме | Инжектирует координату прошлой сессии в system-префикс |

### Правило выбора

`SPEC` Решение принимается **скриптом**, без модели:

```
fill = count_tokens(messages) / num_ctx            # токенизатором модели!
if fill < warn_threshold:                          # напр. 0.60
    if query_touches_known_addresses(query):       # пересечение идентификаторов
        -> ENRICH
    else:
        -> PASSTHROUGH
elif fill < hard_threshold:                        # напр. 0.80
    -> COMPRESS (мягкое: сжать самый старый блок)
else:
    -> COMPRESS (жёсткое: сжать всё до последних K ходов)
```

`PREFETCH` — отдельная ветка: если это первый запрос сессии и в памяти есть
незаархивированная координата, релевантная запросу.

Обратите внимание: **порог задан в долях буфера, а не в количестве сообщений.** Это
прямое следствие решения №3 из `README.md`. Текущий код делает наоборот
(`BROKEN`, `orchestrator.py:307`: `len(self._chat_history) > 12`), из-за чего
настройка `num_ctx` ни на что не влияет (разбор — `03-context-budget.md`).

## 4. Жизненный цикл запроса

`SPEC` Пошагово, с указанием, кто исполняет каждый шаг.

| # | Шаг | Исполнитель | Стоимость |
|---|---|---|---|
| 1 | Принять `POST /v1/chat/completions` | FastAPI | — |
| 2 | Посчитать токены `messages[]` | токенизатор модели (`/tokenize`) | 1 HTTP-вызов, мс |
| 3 | Выбрать режим (PASSTHROUGH / ENRICH / COMPRESS / PREFETCH) | скрипт | арифметика |
| 4 | Если COMPRESS: отобрать срединный отрезок | скрипт (по ledger) | — |
| 5 | Если COMPRESS: собрать Context Package | **координатор** | загрузка в VRAM + генерация |
| 6 | Если COMPRESS: выгрузить координатора | `SwapManager` | выгрузка VRAM |
| 7 | Собрать финальный `messages[]` | скрипт | — |
| 8 | Отправить в движок, стримить ответ клиенту | FastAPI + httpx | генерация |
| 9 | Обновить ledger адресов из ответа | скрипт (парсер) | мс |
| 10 | Записать беседу в архив на диске | скрипт | асинхронно |

Шаги 5–6 выполняются **редко** (раз в несколько тысяч токенов). Шаги 2, 3, 4, 7, 9 —
на каждом запросе, и все они бесплатны по VRAM.

`BROKEN` Текущий код делает обратное: `ImportanceTagger` дёргается **каждый ход**
(`orchestrator.py:521-575`), то есть координатор постоянно в работе. Для нашей
экономики это худший из возможных режимов.

## 5. Требование стабильности префикса (главное ограничение)

Это самый важный технический пункт всего документа.

`llama-server` кэширует KV для обработанного префикса промпта. Если префикс не
изменился, prefill не пересчитывается — новый ход добавляется почти бесплатно. Если
префикс изменился хотя бы на байт, кэш инвалидируется и **весь промпт префиллится
заново**.

Замер влияния, порядок величины: prefill 9B-модели на 8K токенов — это секунды. То есть
наивная реализация «вырезать середину на каждом ходу» превратит отзывчивый движок в
непригодный.

Отсюда три жёстких правила:

1. **Память живёт в фиксированной позиции.** Context Package вставляется в начало
   (system-префикс) и остаётся **байт-идентичным**, пока сессия стабильна.
2. **История растёт только в конец.** Никаких вставок в середину между сжатиями.
3. **Сжатие — редкое пакетное событие.** За него один раз платится полный prefill.
   Пользователь получает плату один раз в N тысяч токенов, а не на каждом ходу.

`SPEC` Практический вывод: порог надо ставить **высоко** (0.80, а не 0.50). Частые
дешёвые сжатия обходятся дороже, чем редкие дорогие.

Идеальная интеграция была бы на уровне слотов/KV внутри `llama-server` (там есть
`n_keep` и управление слотами), но это требует патча C++, а не Python-прокси. Поэтому
принимаем одну плату за prefill на событие сжатия и не пытаемся её обойти.

## 6. Интерфейс

`EXISTS` Прокси обязан быть OpenAI-совместимым — это единственный способ работать с
чужими клиентами без правок на их стороне.

Что обязано поддерживаться:

| Поле | Требование | Текущее состояние |
|---|---|---|
| `messages[]` | чтение и перезапись | `EXISTS` (`system.py:404-410`) |
| `stream: true` | **настоящий** SSE-стрим | `BROKEN` — заглушка (`system.py:322`) |
| `stream: true` на прокси-пути | проброс | `BROKEN` — захардкожен `False` (`system.py:388`) |
| `temperature`, `max_tokens` | проброс | `EXISTS` |
| `model` | проброс имени модели движка | `EXISTS`, но см. ниже |
| `usage` | честный подсчёт токенов | `BROKEN` — оценка `len(...) * 2` (`system.py:419-420`) |

`BROKEN` Отдельно: имена моделей. `_select_model()` возвращает ключи реестра
(`orchestrator.py:651,653`: `"qwen2.5-coder-7b"`, `"qwen3.5-2b"`), а `_generate()`
принимает `model_key` и **не передаёт его в роутер** (`orchestrator.py:753-764`). Поэтому
в ответе клиенту модель указывается не та, что реально работала. Для прокси, где имя
модели приходит от клиента и должно уходить в движок как есть, это надо переписать
целиком, а не править.

## 7. Границы прокси

`SPEC` Что прокси **делает**:

- измеряет заполнение буфера и управляет им;
- решает, что остаётся в окне, а что уходит в память;
- извлекает структурные адреса из трафика (файлы, символы, ошибки);
- собирает Context Package при сжатии;
- хранит память в RAM, архив — на диске.

`SPEC` Что прокси **не делает**:

- не генерирует ответы пользователю;
- не выбирает модель за пользователя;
- не модифицирует семантику запроса (только объём и состав контекста);
- не требует своей GPU-модели, кроме эфемерного координатора.

Последний пункт — причина, по которой в заголовке этой документации стоит «без
генератора». Как только Contextor начинает отвечать сам, он становится обычным чатом с
памятью и теряет единственное преимущество: он больше не влезает рядом с чужой моделью.
