# 02 — Модель памяти

`SPEC` — если не помечено иначе. Этот документ отвечает на вопрос «что именно помнить
и как это устроено». Он самый важный в папке: остальное — механика вокруг него.

---

## 1. Главное отличие от чат-памяти

Обычная «память для LLM» извлекает факты вида *«пользователя зовут Александр»*. Это
работает для болталки и бесполезно для агента, который правит код.

Агентный трафик — это не беседа, а **поток операций над адресами**: файл открыт, функция
изменена, команда выполнена, ошибка получена. Ценность такого трафика почти вся
извлекается **без модели**, потому что это структурированные данные, а не смысл.

Отсюда центральное утверждение документа:

> Для кодинг-агента память — это в первую очередь **индекс адресов**, и только во
> вторую очередь — прозаический конспект.

`SPEC` Это позволяет вынести на скрипты 80–90% работы и дёргать координатор редко.

## 2. Единица памяти: адресный факт

`SPEC` Факт в прокси-режиме — это запись с **адресом**, а не свободный текст.

```python
@dataclass
class AddressedFact:
    # Адрес — то, по чему факт находится за миллисекунды, без эмбеддингов
    kind: str            # file | symbol | decision | contract | error | task | tool
    key: str             # "src/auth.py" | "create_access_token" | "auth.jwt.alg"
    file: str | None     # путь
    symbol: str | None   # имя функции/класса
    lines: tuple[int, int] | None   # диапазон
    # Содержимое
    content: str         # сам текст факта (сигнатура, решение, текст ошибки)
    # Учёт
    version: int         # растёт при обновлении того же адреса
    seen_count: int      # сколько раз встречался
    first_turn: int
    last_turn: int
    weight: float        # вычисляется, не хранится вручную
    tier: str            # hot | warm | anchor | cold
    digest: str          # хеш содержимого — для дедупликации
```

`EXISTS` Ближайший существующий тип — `core/memory/fact.py` (класс `Fact`). У него есть
`content`, `attention_weight`, `is_anchor`, `fact_id`. Полей-адресов **нет** — это первое,
что надо добавить.

### Почему адрес важнее эмбеддинга

Агент спрашивает «что в `auth.py` про токены» — это разрешается точным совпадением по
ключу `auth.py` плюс подстрокой `token`. Векторный поиск здесь не нужен и только вносит
шум. Эмбеддинги остаются для одного случая: **запрос сформулирован словами, без
идентификаторов** («как мы решали проблему с авторизацией»). Это редкий случай, и он
может обслуживаться эмбеддером в RAM, а не в VRAM.

## 3. Слои — это не важность, а близость

`SPEC` В README проекта слои описаны как «важность» (HOT важнее WARM). Это сбивает с
толку. Правильная семантика — **расстояние до окна модели**:

| Слой | Где физически | Что там | Как попадает в окно |
|---|---|---|---|
| **HOT** | в окне модели прямо сейчас | то, что модель видит | уже там |
| **WARM** | RAM, словарь в процессе | весь индекс адресов | по адресному запросу |
| **ANCHOR** | RAM + всегда в префиксе | цель, решения, контракты | всегда в промпте |
| **COLD** | диск | полная беседа, архив | никогда (только для человека) |

`SPEC` Важное следствие: HOT — это **не отдельное хранилище**, а проекция. Нет смысла
«перемещать факт в HOT» — надо изменить состав окна. Текущий код держит HOT как
самостоятельный список (`BROKEN`, `working_memory.py:49`) и потом пытается
синхронизировать его с хранилищем, порождая расхождения.

`BROKEN` В существующем коде слой «Anchor» вообще не слой: это булев флаг `is_anchor`
на факте (`fact.py:53`), лежащем в том же списке. И гарантия «никогда не удаляется» не
выполняется — `_evict_to_budget()` (`working_memory.py:380-389`) выбирает
`min(self._facts, key=attention_weight)` **без проверки `is_anchor`**, хотя
`cleanup()` рядом такую проверку делает (`working_memory.py:155`).

## 4. Ledger — ядро памяти

`SPEC` Основная структура — **ledger**: таблица «адрес → актуальное состояние».

```
src/auth.py
  ├─ секция: импорты            last_turn=12  seen=4
  ├─ symbol: create_access_token  lines=34-41  last_turn=18  seen=3
  ├─ symbol: get_current_user     lines=44-52  last_turn=18  seen=2
  └─ решение: "JWT HS256, exp 30m"  anchor  last_turn=15

src/models.py
  ├─ symbol: User   lines=8-20   last_turn=11  seen=2
  └─ symbol: Todo   lines=22-35  last_turn=17  seen=1

решения (anchor)
  ├─ "SQLite для разработки, PostgreSQL в прод"
  └─ "роуты смонтированы на /api/v1 в main.py"

задача
  ├─ текущая: "добавить тесты pytest"
  └─ сделано: ["JWT auth", "модели User/Todo"]
```

Три свойства, которые дают экономию и которых нет в текущем коде:

1. **Дедупликация по адресу.** Один файл приходит десять раз — в ledger одна запись с
   последней версией и актуальными диапазонами строк. Не десять копий.
2. **Версионность.** `version` растёт при изменении символа; старая версия уходит в
   архив, но не в окно. Модель не видит противоречивых версий одного кода.
3. **Частота как сигнал.** `seen_count` и `last_turn` дают вес арифметикой, без модели.

`SPEC` Ledger живёт в RAM как обычный словарь. Именно это и есть «доставать из
оперативной памяти, а не с диска»: поиск по ключу — микросекунды, без обращения к
диску и без эмбеддингов.

`EXISTS` Основа уже такая: `MemoryStorage` держит факты в словаре в памяти
(`storage.py:205`), JSON — лишь зеркало для персистентности. Ломается не модель
хранения, а то, что **чтение отключено**: единственный вызов извлечения стоит за
`needs_context_restore()`, который всегда `False` (`orchestrator.py:351` +
`cci.py:207-210`). Разбор — `06-known-defects.md`.

## 5. Что делает скрипт, а что модель

`SPEC` Это ответ на ваш вопрос о «максимально облегчить работу скриптами».

### Скрипт — бесплатно, без VRAM, на каждом ходу

| Задача | Как |
|---|---|
| Подсчёт заполнения буфера | токенизатор модели (`/tokenize`) |
| Извлечение путей файлов | регулярные выражения по содержимому сообщений |
| Извлечение символов | `parsers/python_parser.py` (tree-sitter) — **уже есть** |
| Извлечение диффов и диапазонов строк | разбор блоков кода и вывода инструментов |
| Извлечение команд и их кодов возврата | разбор tool-call'ов |
| Извлечение ошибок | шаблоны трейсбеков (`File "..."`, `line N`, `Error:`) |
| Дедупликация и версионирование | сравнение адреса и хеша содержимого |
| Расчёт веса и вытеснение | арифметика по `last_turn`, `seen_count`, размеру |
| Решение о режиме | пороги по заполнению буфера |
| Связность вместо CCI на эмбеддингах | пересечение множеств идентификаторов между ходами |
| Формирование финального `messages[]` | вставка заготовок в стабильные позиции |
| Архив беседы на диск | запись JSON/JSONL |

### Модель — редко, только при сжатии

| Задача | Почему нельзя скриптом |
|---|---|
| Прозаический конспект выброшенного блока | связный текст из фрагментов |
| Слияние противоречивых решений | нужно понимание, а не совпадение строк |
| Разрешение неоднозначности адресов | «та функция про токены» без имени файла |

`SPEC` Пропорция, к которой стоит стремиться: **координатор работает 1 раз на 5–10 тысяч
токенов**, а не на каждом ходу. Текущий код делает наоборот (`BROKEN`,
`ImportanceTagger` вызывается каждый ход, `orchestrator.py:521-575`).

`BROKEN` Дополнительно: `ImportanceTagger` после одной сетевой ошибки **навсегда**
переключается на regex-fallback (`tagger.py:80-91`) и выдаёт мусорные токены вместо
фактов. То есть даже там, где модель должна работать, она может молча не работать.

## 6. Context Package — то, что инжектируется

`SPEC` При сжатии срединный отрезок истории заменяется на четырёхслойный пакет. Идея
взята из архивного `docs/archive/CTX_MODULE_ARCHITECTURE-2026-05-10.md` (UCIP v2), но там она описана как замысел и
в коде отсутствует полностью:

```
[Previous conversation context: <координата, 200-400 токенов>]
[Relevant context from memory: <решения и контракты, 100-200 токенов>]
[Relevant code context: <сигнатуры с адресами, 300-500 токенов>]
[Project structure: <связи, 50-100 токенов>]
```

`SPEC` Требования к формату:

1. **Координата — на английском.** Язык-лингва франко для моделей; русские координаты
  в текущем коде (`BROKEN`, `orchestrator.py:164-177`) — шаблон на русском.
2. **Слой 3 собирается из ledger, а не моделью.** Сигнатуры берутся парсером — модель
  неизбежно переврёт имена.
3. **Каждый слой — отдельное system-сообщение**, как в спецификации.
4. **Позиция фиксирована** (см. `01-architecture.md`, раздел 5) — иначе ломается KV-кэш.
5. **Адаптивный размер** по заполнению буфера: <30% — все слои подробно (~1200 токенов);
   30–60% — сжато (~800); >80% — только координата и решения (~300).

`SPEC` Слой 3 в машинно-читаемом виде (пример):

```
src/auth.py:
  def create_access_token(data: dict, expires_delta: Optional[timedelta] = None) -> str   # 34-41
  async def get_current_user(token: str = Depends(oauth2_scheme)) -> User                 # 44-52
src/models.py:
  class User: id: int, username: str, email: str, hashed_password: str                    # 8-20
```

Именно так выглядит «структурная память», о которой вы говорили: адрес, сигнатура,
диапазон строк. Модель по этому восстанавливает контекст без догадок.

## 7. Что никогда не теряется (инварианты)

`SPEC` Память без инвариантов — это кэш. Список того, что обязано выживать при **любом**
сжатии, вытеснении и перезапуске:

1. **Цель проекта** — формулировка задачи, которую решает пользователь.
2. **Принятые решения** — с обоснованием, чтобы модель не предлагала отвергнутое.
3. **Контракты** — публичные сигнатуры, схемы данных, ключи конфигурации.
4. **Текущий прогресс** — что сделано, что осталось.
5. **Открытые ошибки** — неразрешённые проблемы.

`SPEC` Первые четыре — это и есть `ANCHOR`. Правило: `ANCHOR` не вытесняется никогда,
даже при нехватке бюджета — при переполнении сжимается его **текст**, но не факт
существования.

`BROKEN` Сейчас не выполняется: anchor-факты вытесняются при нехватке бюджета токенов
(`working_memory.py:380-389`), а при сжатии `ENTITY_ONLY` содержимое факта **заменяется
его служебным тегом**: `fact.content = fact.source if fact.source else fact.content[:50]`
(`storage.py:479`). То есть решение с обоснованием превращается в строку `tagger_turn_7`.

## 8. Правила перехода между слоями

`SPEC` Всё арифметика, без модели:

```
# продвижение в ANCHOR
if fact.kind in {decision, contract, goal}:      fact.tier = anchor
elif fact.kind == error and not fact.resolved:   fact.tier = anchor

# вытеснение из окна в RAM
if fill >= hard_threshold:
    evict = sorted(window_facts, key=lambda f: (f.tier == anchor, f.weight))[:n]
    # anchor вытесняется последним

# вес — чистая арифметика
weight = recency(last_turn, current_turn) * 0.5 \
       + log1p(seen_count) * 0.3 \
       + size_penalty(len(content)) * 0.2
```

`SPEC` И `COLD` — только архив для человека. Модель в него не заглядывает; если факт
понадобился, он поднимается в RAM по адресу.

## 9. Как проверить, что память работает

`SPEC` Метрика, которую можно честно измерить (в отличие от «100% recall»):

**Удержание адреса.** Ввести в сессию N уникальных адресов (файл + символ + диапазон),
прогнать M сжатий буфера, затем задать вопросы по каждому адресу и посчитать долю
корректных ответов с точными именами и строками.

- baseline (без памяти): ожидаемо падает до нуля после первого сжатия;
- с памятью: должна оставаться высокой.

Это измеримо скриптом, воспроизводимо и не требует фабрикации базовой линии — в отличие
от `benchmarks/runner.py`, где базовая линия задана захардкоженными нулями
(`06-known-defects.md`, раздел «Бенчмарки»).
