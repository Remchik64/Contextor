# 05 — План внедрения

`SPEC` — если не помечено иначе. Порядок работ с указанием конкретных файлов и
критериев приёмки.

Принцип упорядочивания: **сначала то, без чего нельзя измерить результат.** Пока буфер
не измеряется в токенах, любое утверждение о памяти недоказуемо, и мы повторим ошибку
исходного репозитория — будем описывать несуществующее как работающее.

## Оценка и риски

`SPEC` Порядок величины, не обещание:

| Фаза | Объём |
|---|---|
| 0 | часы (четыре правки + безопасность) |
| 1 | дни — ядро, требует аккуратности в подсчёте |
| 2 | неделя-полторы — самая содержательная часть |
| 3 | неделя — интеграция swap и сборка пакета |
| 4 | дни — транспорт |
| 5 | дни |

### Главные риски

1. **KV-кэш.** Сжатие ломает prefill. Если на вашей сборке цена окажется выше ожидаемой,
   придётся поднимать порог и увеличивать глубину сжатия. Проверять замером в Фазе 1,
   не позже.
2. **Сценарий B.** Агент может не переживать подмену своей истории. Не начинать с него.
3. **Точность токенизации.** Если `/tokenize` недоступен, запас 15–20% обязателен,
   иначе переполнение.
4. **Соблазн вернуть генератор.** Как только Contextor начнёт отвечать сам, он
   перестанет влезать рядом с чужой моделью — и потеряет единственное преимущество.
