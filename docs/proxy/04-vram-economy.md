# 04 — Экономика VRAM

`SPEC` — если не помечено иначе. Документ о том, почему схема вообще выгодна и как
посчитать выгоду для конкретной модели.

---

## 1. Контекст — это VRAM

Ваша формулировка «не хочу забивать слои GPU контекстом» верна арифметически. Размер
KV-кэша линейно зависит от длины окна:

```
KV_байт = 2 · n_layers · n_kv_heads · head_dim · ctx · bytes_per_element

  2                  — отдельно ключи (K) и значения (V)
  n_layers           — число слоёв модели
  n_kv_heads         — число KV-голов (при GQA их меньше числа attention-голов)
  head_dim           — размерность головы (обычно 128)
  ctx                — длина контекста в токенах
  bytes_per_element  — 2 для fp16, 1 для q8_0, ~0.5 для q4_0
```

### Посчитанные примеры (fp16)

| Модель | Слои | KV-голов | KiB/токен | 4K | 8K | 16K | 32K |
|---|---:|---:|---:|---:|---:|---:|---:|
| Qwen2.5-7B | 28 | 4 | 56 | 224 МБ | 448 МБ | 896 МБ | **1.75 ГБ** |
| Llama-3.1-8B | 32 | 8 | 128 | 512 МБ | 1.0 ГБ | 2.0 ГБ | **4.0 ГБ** |
| Qwen2.5-14B | 48 | 8 | 192 | 768 МБ | 1.5 ГБ | 3.0 ГБ | **6.0 ГБ** |
| Qwen2.5-32B | 64 | 8 | 256 | 1.0 ГБ | 2.0 ГБ | 4.0 ГБ | **8.0 ГБ** |

### Сколько освобождается при переходе с 32K на 4K

| Модель | Освобождается |
|---|---:|
| Qwen2.5-7B | **1.5 ГБ** |
| Llama-3.1-8B | **3.5 ГБ** |
| Qwen2.5-14B | **5.25 ГБ** |
| Qwen2.5-32B | **7.0 ГБ** |

`SPEC` Дополнительный рычаг: квантизация самого KV-кэша (`--cache-type-k q8_0`,
`--cache-type-v q8_0` в `llama.cpp`) делит эти числа вдвое почти без потери качества.
То есть 32K на q8_0 стоит как 16K на fp16. Это ещё один способ вернуть гигабайты, и он
не требует менять архитектуру.

**Как посчитать для своей модели:** возьмите `n_layers`, `n_kv_heads`, `head_dim` из
карточки модели (или из `llama-server` в логе загрузки) и подставьте в формулу.
Число `n_kv_heads` — не число attention-голов; при GQA оно в 4–8 раз меньше, и именно
поэтому KV-кэш современных моделей не катастрофичен.

## 2. Честный расчёт: окупается ли координатор

Здесь важно не обмануть самих себя, поэтому считаем прямо.

### Стоимость координатора

| Компонент | VRAM |
|---|---:|
| 2B в Q4_K_M (веса) | ~1.2–1.5 ГБ |
| Его собственный KV при окне 4K | ~0.1 ГБ |
| Эмбеддер (all-MiniLM-L6-v2) | ~0.09 ГБ, **может жить на CPU** |
| **Итого, если резидентно** | **~1.5 ГБ** |

### Сравнение

| Модель | Освобождено (32K→4K) | Координатор резидентный | Чистый итог |
|---|---:|---:|---:|
| Qwen2.5-7B | 1.5 ГБ | −1.5 ГБ | **≈ 0** |
| Llama-3.1-8B | 3.5 ГБ | −1.5 ГБ | **+2.0 ГБ** |
| Qwen2.5-14B | 5.25 ГБ | −1.5 ГБ | **+3.75 ГБ** |
| Qwen2.5-32B | 7.0 ГБ | −1.5 ГБ | **+5.5 ГБ** |

**Вывод, который надо принять открыто:** на 7B с резидентным координатором выигрыша по
VRAM нет. Он появляется с 14B и растёт с размером модели.

Поэтому для 7B аргумент должен быть не про VRAM, а про **качество**: сессия не
деградирует. Врать про «экономию памяти» на 7B нельзя — это проверяется формулой за
минуту.

## 3. Координатор обязан быть эфемерным

`SPEC` Это решение устраняет проблему выше полностью. Координатор нужен **только в
момент сжатия** — он загружается, сжимает, выгружается. Всё остальное время память под
него отдана генератору.

Тогда:

| Модель | Освобождено | Координатор (эфемерный) | Чистый итог |
|---|---:|---:|---:|
| Qwen2.5-7B | 1.5 ГБ | 0 постоянно | **+1.5 ГБ** |
| Qwen2.5-14B | 5.25 ГБ | 0 постоянно | **+5.25 ГБ** |
| Qwen2.5-32B | 7.0 ГБ | 0 постоянно | **+7.0 ГБ** |

Плюс: сжатие происходит редко (раз в 5–10 тысяч токенов), поэтому цена загрузки/выгрузки
весов окупается. На NVMe 1.2 ГБ читаются за ~0.1 с, на SATA — за ~2–3 с. Для события,
случающегося раз в несколько минут, это допустимо.

### Механизм уже написан

`EXISTS` `src/contextor/utils/swap_manager.py` — `ModelSwapManager` (200 строк):
загрузка модели в VRAM, выгрузка, **подтверждение** выгрузки, восстановление
эмбеддера. Методы `acquire_coordinator` / `release_coordinator`
(`swap_manager.py:123,138`).

`DEAD` Вызывается только из `utility_worker.py:125,140`, то есть не в нашем сценарии.
Покрытие тестами — 0%.

`SPEC` Для архитектуры прокси это **не утилита, а центральный механизм**. Его надо
переиспользовать как есть, а не писать заново.

`VERIFY` Проверить на вашей сборке: как `ModelSwapManager` общается с движком. Судя по
логам (`swap_manager.py:57,81`), он работает через Ollama-совместимые вызовы
загрузки/выгрузки. Для `llama-server` модель выгружается иначе — процессом или
перезапуском слота. Возможно, потребуется второй бэкенд для swap.

### Альтернатива: координатор на CPU

`SPEC` Рассмотреть как вариант по умолчанию для слабых карт: 2B в Q4 на CPU выдаёт
порядка 10–30 токенов/с. Конспект на 300 токенов — это 10–30 секунд ожидания при
сжатии. Если сжатие происходит раз в несколько минут, это может быть приемлемо, а VRAM
не тратится вообще.

Сравнение вариантов:

| Вариант | VRAM | Задержка сжатия | Сложность |
|---|---|---|---|
| Эфемерный на GPU | 0 постоянно | загрузка ~0.1–3 с + генерация ~1–2 с | средняя (swap) |
| На CPU | 0 | 10–30 с | низкая |

`SPEC` Рекомендация: эфемерный GPU как основной режим, CPU — как fallback-профиль.

### Эмбеддер — всегда на CPU

`SPEC` `all-MiniLM-L6-v2` — 22M параметров, ~90 МБ. На CPU считает быстрее, чем успевает
понадобиться. Держать его в VRAM незачем. Текущий код по умолчанию идёт в Ollama за
эмбеддингами (`storage.py:154`), то есть занимает VRAM движка зря.

## 4. Что покупается на освобождённые гигабайты

`SPEC` Три варианта, по возрастанию полезности:

1. **Больше слоёв на GPU** (`-ngl`). Прямо ускоряет генерацию. На 14B разница между
   50% и 100% слоёв на GPU — это разы по скорости, а не проценты.
2. **Больше параллельных слотов** (`--parallel`). Больше одновременных агентов на той
   же карте. Для прокси, через который работают несколько инструментов, это прямая
   пропускная способность.
3. **Модель большего размера.** Главное: 7B → 14B при той же VRAM — это качество
   ответов, которое ничем другим не купить.

Именно пункт 3 делает схему осмысленной как продукт: вы меняете длину контекста, которую
модель всё равно не умеет использовать, на параметры, которые она умеет.

## 5. Взаимодействие с KV-кэшем при сжатии

`SPEC` Тут пересекаются две экономики, и их надо держать в голове вместе.

**VRAM-экономика** говорит: держите окно маленьким, сжимайте часто.
**Экономика prefill** (см. `01-architecture.md`, раздел 5) говорит: сжатие ломает
KV-кэш, поэтому сжимайте редко.

Компромисс — **редкое, но глубокое сжатие**: порог 0.85, после сжатия окно опускается
до ~0.25 заполнения. Тогда вы платите один prefill на длинный отрезок работы.

`SPEC` Полезный ориентир: при `num_ctx=8192`, пороге 0.85 и удержании 4 ходов цикл
выглядит так: сжатие раз в ~7K новых токенов, окно колеблется между 2K и 7K. При
генерации ~15 ток/с это событие раз в ~8 минут.

`VERIFY` `llama-server` умеет переиспользовать KV только для неизменного префикса.
Точное поведение зависит от версии и от того, использует ли клиент один слот. Проверить
замером: время до первого токена на повторном запросе с неизменным префиксом против
запроса после сжатия. Разница покажет фактическую цену сжатия на вашей сборке.

## 6. Итоговая экономическая модель

`SPEC` Собираем всё вместе. Для машины с 12 ГБ VRAM (RTX 3060 12GB — рекомендованное
железо проекта) и модели 14B Q4_K_M (~9 ГБ весов):

| Статья | Без прокси (окно 32K) | С прокси (окно 4K) |
|---|---:|---:|
| Веса 14B Q4 | 9.0 ГБ | 9.0 ГБ |
| KV-кэш | 6.0 ГБ | 0.75 ГБ |
| Координатор | — | 0 (эфемерный) |
| Эмбеддер | 0.4 ГБ (Ollama) | 0 (CPU) |
| **Итого** | **15.4 ГБ — не влезает** | **9.75 ГБ — влезает** |

Это и есть реальный аргумент: без прокси модель с окном 32K на такой карте не
запускается вообще, либо часть слоёв уходит на CPU и генерация замедляется в разы. С
прокси — влезает целиком.

Возможность проверить это утверждение есть всегда: формула выше даёт числа за минуту,
а `nvidia-smi` показывает фактические. Ни одного числа, которое нельзя перепроверить.
