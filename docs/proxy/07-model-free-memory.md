# 07 — Скриптовая память без модели

`SPEC` — если не помечено иначе. Документ описывает реализацию памяти **полностью на
скриптах**, без координатора, без эмбеддингов, без обращений к какой-либо модели.

Это самый дешёвый и самый предсказуемый вариант: одна зависимость меньше, ноль VRAM под
память, никаких сетевых задержек внутри хода, полная воспроизводимость (одинаковый вход
даёт одинаковый выход).

---

## 1. Что мы теряем и что остаётся

Решение отказаться от модели — сильное, и надо ясно понимать его цену.

| Теряем | Остаётся |
|---|---|
| Прозаический конспект «о чём говорили» | Точные адреса: файл, символ, диапазон строк |
| Автоматическое распознавание «цели» и «решений» | Сигнатуры функций и классов — **без искажений** |
| Разрешение неоднозначных запросов словами | Диффы, команды, коды возврата, трейсбеки |
| | Счётчики, версии, частота, давность |
| | Полный детерминизм и нулевая задержка |

**Ключевой вывод:** для кодинг-агента это почти без потерь. Модель нужна была для
«связной прозы», а в агентном трафике ценность почти вся — в адресах и сигнатурах, и
именно там модель бы только навредила: она перевирает имена функций и номера строк.

Честная оговорка: для свободного чата (без кода и инструментов) этот вариант даёт мало —
там извлекать структурно почти нечего. Если нужен и чат, понадобится либо модель, либо
ручное пинирование (см. раздел 6).

## 2. Проходы: сколько раз обходим данные

Это ответ на вопрос «оцени проходы». Ключевое решение — **объединить подсчёт токенов и
извлечение адресов в один обход**, потому что оба нужны на каждом запросе и оба линейны
по токенам.

| Момент | Проходов | Что делается | Стоимость |
|---|---:|---|---|
| Обычный запрос (без сжатия) | **1** | подсчёт токенов + извлечение адресов из новых сообщений | O(новые токены) |
| Сжатие | **2** | то же + обход выброшенного отрезка для обновления ledger | O(выброшенный отрезок) |
| Старт сессии | 1 | чтение ledger с диска в RAM | O(размер ledger) |
| Сохранение (асинхронно) | 0 в критическом пути | запись ledger на диск | вне запроса |

Важное: обход **инкрементальный**, а не по всей истории. Хранится «водяной знак» —
индекс последнего обработанного сообщения. На каждом запросе обрабатываются только новые
сообщения, поэтому стоимость не растёт с длиной беседы.

```
водяной_знак = 42
новых сообщений = 3          # клиент прислал 45, обрабатываем 43-45
стоимость = O(токены этих 3)  # а не O(токены всех 45)
```

Это критично: наивная реализация, обходящая весь `messages[]` каждый запрос, на длинной
сессии деградирует линейно и съест весь выигрыш от маленького буфера.

### Что в проходе №1

За один обход каждого нового сообщения делаем всё сразу:

```
для каждого нового сообщения:
    tokens += tokenize(содержимое)          # подсчёт для бюджета
    извлечь(содержимое) → адреса            # regex + tree-sitter
    обновить ledger(адреса)
```

Токенизация — единственная внешняя операция. Её можно сделать локальной (см. раздел 3),
тогда проход вообще не выходит за пределы процесса.

## 3. Шаг 1: измерение буфера

`SPEC` Три варианта, по убыванию точности:

| Вариант | Точность | Стоимость | Когда использовать |
|---|---|---|---|
| `POST /tokenize` у `llama-server` | точная | 1 HTTP на запрос | основной режим |
| Локальный HF-токенизатор той же модели | точная | ~мс в процессе | если `/tokenize` недоступен |
| Оценка `len(текст) / 3.5` с запасом | ±20% | 0 | только как fallback |

`VERIFY` Доступность `/tokenize` и форма ответа зависят от версии `llama-server`.
Проверить первым делом: `curl -X POST localhost:8080/tokenize -d '{"content":"привет"}'`.

`SPEC` Токенизацию лучше вынести в отдельный маленький модуль-обёртку с кэшем по хешу
содержимого: одни и те же сообщения (system-префикс, anchor-блок) не меняются между
запросами, их токены надо посчитать один раз.

```python
# proxy/tokens.py — эскиз
from functools import lru_cache

@lru_cache(maxsize=4096)
def _count_cached(text_hash: str, text: str) -> int: ...

def count(text: str) -> int:
    return _count_cached(hashlib.blake2b(text.encode()).hexdigest(), text)
```

## 4. Шаг 2: извлечение адресов

`SPEC` Всё, что нужно, извлекается детерминированно. Ниже — полный перечень сигналов.

### 4.1 Пути файлов

Регулярные выражения по расширениям и по кавычкам:

```
(?:^|\s)([\w./\\-]+\.(?:py|js|ts|tsx|go|rs|java|rb|php|c|cpp|h|hpp|cs|sh|sql|ya?ml|toml|json|md))
```

Плюс нормализация: привести `\` к `/`, убрать `./`, схлопнуть `..`.

### 4.2 Символы и диапазоны строк

`EXISTS` `src/contextor/parsers/python_parser.py` — tree-sitter-парсер, уже в
зависимостях. Даёт классы и функции с диапазонами строк.

`SPEC` Для остальных языков при отсутствии парсера — регулярные выражения
(`def`, `class`, `func`, `function`, `fn`, `public ... {`, `interface`) с эвристикой по
отступам. Точность ниже, но для Python (основной случай) парсер точен.

### 4.3 Диффы

```
^@@ -\d+(?:,\d+)? \+(\d+)(?:,\d+)? @@      # заголовок ханка → диапазон
^\+[^+]                                     # добавленные строки
^-[^-]                                      # удалённые строки
```

Из диффа извлекаем: какие файлы менялись, какие диапазоны затронуты, какие символы
появились или изменились (по заголовкам ханков и по контексту).

### 4.4 Команды и коды возврата

Из tool-call'ов и блоков вывода:

```
\$ (.+)                       # команда оболочки
^\s*[✗✘]|exit code (\d+)|returncode=(\d+)
```

Интересны только неуспешные команды и те, чей вывод содержит ошибку.

### 4.5 Трейсбеки и ошибки

```
File "([^"]+)", line (\d+)          # точка в трейсбеке → файл + строка
^(\w*Error|\w*Exception):\s*(.+)$   # тип и текст ошибки
walidacja|Traceback \(most recent
```

`SPEC` Ошибка считается открытой, пока в последующих сообщениях не появится признак
успеха для того же адреса (тот же файл/символ без трейсбека).

### 4.6 Контракты

Изменения сигнатур — самый ценный сигнал для агента, потому что ломает вызовы:

```
^\s*(?:async\s+)?def\s+(\w+)\s*\(([^)]*)\)\s*(?:->\s*([^:]+))?
^\s*class\s+(\w+)\s*(?:\(([^)]*)\))?
```

Если сигнатура символа в новой версии отличается от сохранённой — фиксируем изменение
контракта: старое и новое, плюс версия.

### 4.7 Ключи конфигурации

```
^\s*([a-z_][\w.]*)\s*[:=]\s*(.+)$      # в yaml/toml/ini/конфиг-блоках
```

Позволяет помнить «в проекте `num_ctx: 8192`», не пересказывая файл.

## 5. Шаг 3: Ledger

`SPEC` Полная структура — в `02-memory-model.md`. Здесь — только операции, все O(1) на
факт.

```python
class Ledger:
    def upsert(self, fact: AddressedFact) -> None:
        """Обновить по адресу. Дедупликация по digest."""
        key = (fact.kind, fact.key)
        old = self._facts.get(key)
        if old is None:
            fact.version, fact.seen_count, fact.first_turn = 1, 1, fact.last_turn
            self._facts[key] = fact
        elif old.digest == fact.digest:
            old.seen_count += 1
            old.last_turn = fact.last_turn          # только учёт, содержимое не трогаем
        else:
            fact.version = old.version + 1
            fact.seen_count = old.seen_count + 1
            self._facts[key] = fact                 # старая версия уходит в архив
            self._archive.append(old)

    def find(self, needle: str) -> list[AddressedFact]:
        """Поиск по адресу: точное совпадение ключа, затем подстрока."""
        ...
```

`SPEC` Вес считается арифметикой, без модели:

```python
def weight(f, current_turn) -> float:
    recency = 1.0 / (1.0 + (current_turn - f.last_turn) * 0.15)
    freq    = math.log1p(f.seen_count) / 3.0
    size    = 1.0 - min(len(f.content) / 2000.0, 1.0)
    return 0.5 * recency + 0.3 * freq + 0.2 * size
```

`SPEC` Anchor-факты (`decision`, `contract`, `goal`, открытые `error`) не участвуют в
вытеснении никогда. При нехватке места сжимается их **текст**, но не факт существования.

## 6. Шаг 4: что делать без модели с «целью» и «решениями»

Это самое слабое место модели-независимого варианта, и здесь нужна честность: нельзя
надёжно определить «главную цель пользователя» регулярками.

`SPEC` Решение из двух частей.

### Часть 1 — эвристики (дают часть, не всё)

| Сигнал | Правило |
|---|---|
| Явные маркеры | строки с `TODO:`, `FIXME:`, `NOTE:`, `IMPORTANT:`, `Decision:`, `Решение:`, `Цель:`, `Задача:` |
| Настойчивость темы | файл/символ, упомянутый ≥3 раз за последние 10 ходов → текущий фокус |
| Смена контракта | изменение сигнатуры → anchor (ломает вызовы) |
| Неразрешённая ошибка | трейсбек без последующего успеха → anchor |
| Заголовок задачи | первое сообщение сессии, если короче 300 токенов → «постановка» |

### Часть 2 — явное пинирование (надёжный путь)

`SPEC` Вместо угадывания дать возможность **сказать прямо**. Три способа:

1. **Соглашение в тексте.** Сообщение, начинающееся с `#anchor:`, целиком сохраняется
   как anchor. Работает с любым клиентом, не требует API.
2. **HTTP-ручка.** `POST /api/v1/proxy/anchors` с телом `{"key": "...", "content": "..."}`
   — для инструментов и скриптов агента.
3. **Кнопка в интерфейсе.** Ручное добавление/редактирование якорей
   (см. `08-proxy-ui.md`, вкладка «Память»).

`SPEC` Приоритет: часть 2 надёжнее части 1. Если агент способен вызвать инструмент — он
сам объявит цель и решения, и никакие эвристики не нужны.

## 7. Шаг 5: сборка Context Package без модели

`SPEC` Так как прозы нет, блок собирается из ledger «как есть» — адреса и сигнатуры. Это
не хуже: агент получает точные имена вместо пересказа.

```
[CTX MEMORY — anchors]
goal: add pytest tests for the auth module            (pinned, turn 3)
decision: JWT HS256, exp 30m                          (turn 15)
decision: SQLite for dev, PostgreSQL for prod         (turn 8)
open error: sqlite3.OperationalError in db.py:41      (turn 22)

[CTX MEMORY — code (ledger)]
src/auth.py  v3  seen=4  last=turn 18
  def create_access_token(data: dict, expires_delta: Optional[timedelta] = None) -> str   # 34-41
  async def get_current_user(token: str = Depends(oauth2_scheme)) -> User                 # 44-52
src/models.py  v2  seen=2  last=turn 17
  class User: id: int, username: str, email: str, hashed_password: str                    # 8-20

[CTX MEMORY — recent commands]
$ pytest tests/test_auth.py  → exit 1                        (turn 22)
$ curl -X POST /api/v1/login → 422                           (turn 20)
```

`SPEC` Размер блока — по заполнению буфера, но **детерминированно**:

| Заполнение | Что включать | Ориентир |
|---|---|---:|
| < 0.30 | всё: anchors + код + команды + ошибки | ~1200 токенов |
| 0.30–0.60 | anchors + код | ~800 |
| 0.60–0.80 | только anchors + топ-5 символов по весу | ~450 |
| > 0.80 | только anchors | ~200 |

`SPEC` Порядок секций **фиксирован**, и внутри секций сортировка устойчива (по адресу,
не по весу) — иначе блок будет меняться между запросами на пустом месте и ломать
KV-кэш движка (см. `01-architecture.md`, раздел 5).

Это важная деталь: сортировать по весу нельзя, потому что вес меняется каждый ход.
Сортировать надо по адресу, а отбирать по весу. Отбор — на входе, порядок — стабильный.

## 8. Шаг 6: хирургия контекста

`SPEC` Финальная сборка промпта:

```
[0] system: <роль клиента, если была>
[1] system: <CTX MEMORY блок>          ← ФИКСИРОВАННАЯ ПОЗИЦИЯ
[2..2+K-1] последние K ходов           ← K = 4..8
```

Правила:

1. **Блок памяти всегда на позиции 1** (после system клиента, если он есть). Не в конце,
   не в середине — иначе KV-кэш инвалидируется на каждом ходу.
2. **`messages` между блоком и хвостом удаляются** — они уже отражены в ledger.
3. **Хвост берётся по границе хода.** Никогда не разрывать пару
   `assistant(tool_call) → tool(result)`: агент на этом падает. Резать только по
   `role == "user"`.
4. **system-сообщения клиента сохраняются** и склеиваются с блоком, а не заменяются.
   `BROKEN` Текущий код делает наоборот: `orchestrator.py:444` при наличии `system`
   полностью пропускает сборку контекста.

```python
def assemble(messages, ctx_block, keep_turns=6) -> list[dict]:
    systems = [m for m in messages if m["role"] == "system"]
    tail    = last_turns(messages, keep_turns)   # граница по role == "user"
    return [*systems, {"role": "system", "content": ctx_block}, *tail]
```

## 9. Шаг 7: персистентность и перезапуск

`SPEC` Ledger пишется на диск асинхронно, вне критического пути запроса.

| Что | Куда | Когда |
|---|---|---|
| Ledger (факты + anchors) | `storage/proxy/<session>/ledger.json` | раз в N секунд или по N изменений |
| Полная беседа | `storage/proxy/<session>/history.jsonl` | append на каждом ходу |
| Конфигурация | один файл, см. `08-proxy-ui.md` | при изменении |

`BROKEN` Обязательное требование, которое сейчас нарушено: **все** операции
чтения/записи — с `encoding="utf-8"`. Сейчас `working_memory.py:249` и `storage.py:551`
пишут в кодировке локали (cp1251), а читают как utf-8, из-за чего русский текст
уничтожается, а со второго сохранения сессия теряется целиком (разбор —
`06-known-defects.md`, D.1).

`SPEC` `history.jsonl` — формат «одна строка — одно сообщение». Даёт два преимущества:
append без перезаписи файла и возможность читать хвост, не поднимая всё в память.

## 10. Шаг 8: что проверить, прежде чем считать готовым

| Проверка | Как | Ожидание |
|---|---|---|
| Буфер не переполняется | логировать фактический `fill` перед каждым запросом | ни разу > `num_ctx` |
| `num_ctx` влияет | 4096 против 16384 | момент сжатия сдвигается |
| Адрес удерживается | N адресов, M сжатий, вопросы | точные имена и строки |
| Один файл — одна запись | 50 обращений к файлу | в ledger 1 запись, `seen_count=50` |
| Стоимость не растёт | 10 и 100 ходов | время обработки на ход не растёт |
| Перезапуск | убить и поднять | anchors и адреса на месте, русский текст цел |
| Пара не рвётся | сессия с tool-call'ами | нет сообщений `tool` без предшествующего `assistant` |

| 6 | Сборка блока из ledger | 1 день |
| 7 | Хирургия контекста | 1 день |
| 8 | Персистентность и перезапуск | 1 день |
| 9 | Интерфейс настройки (`08-proxy-ui.md`) | 2–3 дня |
| 10 | Проверки из раздела 10 | 1.5 дня |

`SPEC` Самая большая и самая ценная часть — шаг 4 (извлечение). Именно она определяет
качество памяти: если адреса извлекаются точно, всё остальное работает предсказуемо,
потому что вся дальнейшая логика — арифметика над уже извлечённым.

### Что можно сделать быстрее

Минимальная версия за ~3–4 дня: шаги 1, 2, 3, 7 без извлечения адресов вообще.
Это прокси, который **гарантированно не переполняет окно** и режет историю по границам
ходов. Памяти ещё нет, но продукт уже полезен — и это первое, что стоит показать.

## 12. Главный риск варианта без модели

`SPEC` Не качество памяти, а **сложность извлечения**. Агентный трафик разнороден:
разные инструменты, разные форматы вывода, разные языки. Регулярные выражения придётся
дополнять по мере встречи с новыми форматами, и это работа без конца.

`SPEC` Смягчение: сделать извлечение **подключаемым** — набор мелких экстракторов с
общим интерфейсом, каждый со своим тестом на реальном образце вывода. Тогда новый
формат = новый экстрактор, а не правка общей логики.

```python
class Extractor(Protocol):
    name: str
    def extract(self, message: dict) -> Iterable[RawAddress]: ...
```

И держать `tests/extractors/` с реальными кусками логов и выводов — тогда добавление
поддержки нового инструмента становится механическим.
